Torus / QUANTA — Audit & Feuille de route

Diagnostic franc et priorisé pour passer d'un prototype d'ingénieur talentueux à un produit perçu comme professionnel. Code · Sécurité · Produit · Crédibilité · Production.

Commit 4d98fed Branche feat/v3.3-production Date 2026-05-31 ~26 700 LOC 256 tests 70 commandes Tauri Public équipe technique

Le moteur est plus professionnel que le projet.

L'ingénierie est sérieuse : crypto à l'état de l'art, pipeline de réception P2P complet et signé, ~5 unwrap en production seulement, 0 unsafe, CI avec clippy -D warnings, updater OTA réellement signé. Ce qui fait « amateur » n'est presque jamais le code — c'est la couche externe : un README qui décrit un autre produit, une marque éclatée en 5 noms, des versions incohérentes, aucune licence, et quelques promesses post-quantiques que le code lui-même contredit honnêtement. Bonne nouvelle : l'essentiel de ce déficit se corrige en jours, pas en mois.

Socle technique solide, vitrine amateur

La note globale est tirée vers le bas par la crédibilité (33) et la prod-readiness (52) — précisément les deux dimensions les moins coûteuses à redresser. Un projet « google web3 » se juge d'abord sur sa vitrine ; ici la vitrine ment sur la qualité réelle du code.

◆ Déjà solide (à préserver)

  • Crypto : Ed25519 par enveloppe, AES-256-GCM, Argon2id 64 Mo, BLAKE3, zeroize + ZeroizeOnDrop.
  • Pipeline réception : taille → ban → dedup → fraîcheur → rate-limit adaptatif → nonce → signature.
  • Discipline Rust : ~5 unwrap en prod, 0 unsafe, 0 TODO, clippy -D warnings en CI.
  • 256 tests dont convergence multi-nœuds (in-process) + property-testing (proptest).
  • Updater OTA réellement configuré (clé minisign + endpoints).
  • Onboarding : wizard chiffré, auto-lock, StrengthMeter, Cmd+K, 48 attributs a11y.

▲ Ce qui bloque le « pro »

  • README ≠ produit : décrit 15 commandes, Willow/Lightning, v0.4.0 — le code en a 70 et fait tout autre chose.
  • Marque éclatée : Torus / Quanta / Sovereign Web Engine / SOVA / Willow.
  • Post-quantique survendu alors que ML_DSA_AVAILABLE = false.
  • Versions incohérentes : 0.1.0 / 0.4.0 / 1.0.0 / 1.0.1 ; aucun tag git.
  • Aucune LICENSE ; package.json encore nommé tauri-app.
  • Robustesse réseau réelle prouvée par un seul test manuel à 2 machines.
  • Clé de récupération non forcée sur le parcours d'onboarding principal.

Méthodologie & périmètre

Comment lire ce rapport, et la limite de ce qui a été audité.

Périmètre
Audit 360° à 4d98fed (branche feat/v3.3-production) : backend Rust (src-tauri/src, 18 874 l.), frontend Svelte (src, 7 819 l.), configuration prod, dépôt, docs publiques (README, 2 whitepapers).
Méthode
Lecture ciblée des modules critiques (pipeline gossip, ledger, consensus PoS, crypto, dev-API, app-shell), mesures reproductibles (rg, wc, git), recoupement code ↔ docs pour détecter les écarts de discours. Chaque finding cite une preuve fichier:ligne.
Notes & sévérité
Les scores sont une évaluation d'expert, pas une métrique automatique. Sévérité = impact sur la qualité/perception « pro ». Effort : S = heures, M = jours, L = semaines. Les findings positifs sont inclus volontairement pour un diagnostic honnête.
Transparence d'une correction
Une première passe brute comptait « ~238 unwrap ». Re-mesuré proprement (hors modules #[cfg(test)]), le chiffre réel en production est ≈5, tous bénins. Ce rapport reflète la réalité, pas la première impression.
Hors périmètre
Pas de test de pénétration réseau live, pas d'audit cryptographique formel, pas de revue exhaustive des 70 commandes. Les angles morts sont signalés comme tels (ex. D1).

Architecture & qualité de code

Constat

Pourquoi ça compte

A1MoyenFichiers monolithiques (jusqu'à 3 113 lignes)effort M▶
Constat

Lisibilité et revue de la surface d'attaque IPC dégradées ; difficile de savoir d'un coup d'œil ce qui est exposé au frontend.
Recommandation
Regrouper les commandes par domaine (façade commands/{wallet,sites,social,network}.rs) et documenter la liste exposée. Pas urgent, mais clarifie la frontière app↔cœur.
B

Sécurité & cryptographie

2 positifs · 4 axes
B0aPositifPipeline de réception P2P complet & signé—▶
Constat
Chaque enveloppe entrante traverse 8 garde-fous avant traitement.
// dispatcher.rs : dispatch_incoming()
:225  taille max 10 Mo
:243  ban check (par pair)
:245  dedup (seen_messages LRU)
:278  fraîcheur timestamp (±90 s)
:289  rate-limit adaptatif
:304  nonce monotone par sender
:318  Ed25519 (canonique STRUCT-1)
Pourquoi ça compte
C'est exactement la défense en profondeur attendue d'un protocole P2P sérieux. Verify-before-process correctement implémenté.
B0bPositifPrimitives crypto à l'état de l'art + gestion des secrets—▶
Constat
Ed25519 (ed25519-dalek 2.2), AES-256-GCM, Argon2id (64 Mo), BLAKE3. Les secrets sont effacés : plaintext.zeroize() après chiffrement (cipher.rs:45), sk_bytes.zeroize() (pq_vault.rs:85), SecureBuffer #[derive(Zeroize, ZeroizeOnDrop)] (mod.rs:111).
Pourquoi ça compte
Conforme aux propres règles du projet (zeroize, Ed25519 partout). Rien à corriger ici — c'est un argument de vente réel, à condition de ne pas le survendre (cf. B1).
B1ÉlevéPost-quantique annoncé partout, désactivé dans le codeeffort S▶
Constat
La couche ML-DSA-65 est un stub explicite. Le code est honnête ; ce sont les docs qui ne le sont pas (cf. F2).
// hybrid_crypto.rs
:51  const ML_DSA_AVAILABLE: bool = false;
:93  sign() → quantum: Vec::new()   // jamais de signature PQ
:180 verify_ml_dsa() → false        // seconde ceinture
Impact
Aucun risque technique (fallback Ed25519 propre, testé). Mais risque réputationnel majeur : en crypto, annoncer une protection inexistante détruit la confiance dès qu'un expert lit le code.
Recommandation
Décider explicitement : soit (a) activer ML-DSA quand ml-dsa ≥ 0.2 sera compatible (et arbitrer OR vs AND), soit (b) requalifier tout le discours externe en « post-quantum-ready » (roadmap). Tant que (a) n'est pas fait, faire (b) immédiatement.
B2MoyenAnti-Sybil réel ≠ anti-Sybil documentéeffort S▶
Constat
Le README décrit des « S/Kademlia crypto puzzles (~500 ms CPU pour rejoindre) ». La réalité (sybil.rs:1) est un Proof-of-Contribution : score uptime×0.35 + énergie×0.30 + stake×0.25 + ancienneté×0.10 qui pondère le mining — pas un puzzle d'admission.
Impact
Mécanisme légitime, mais différent et plus faible comme défense Sybil que ce qui est annoncé. Un attaquant ne « paie » pas à l'entrée ; il accumule un score dans le temps.
Recommandation
Aligner la doc sur le mécanisme réel (PoC économique), et — si la résistance Sybil est un argument central — ajouter un vrai coût d'admission (puzzle BLAKE3 ou stake minimal vérifié au join).
B3FaibleContournement de l'anti-replay pour nonce == 0effort S▶
Constat
dispatcher.rs:304 — la vérification monotone du nonce est sautée si nonce == 0 (compatibilité messages legacy). Le dedup par ID + la fraîcheur ±90 s compensent partiellement.
Impact
Fenêtre de rejeu théorique réduite mais non nulle pour des messages forgés à nonce=0 dans la fenêtre de fraîcheur.
Recommandation
Une fois la migration de protocole terminée (tous les pairs émettent un nonce > 0), rejeter nonce == 0. Documenter la date de bascule.
B4FaibleAuth dev-API fragile sur token videeffort S▶
Constat
dev_api.rs:371 : ensure_token().unwrap_or_default() → token vide si la lecture disque échoue. La comparaison h.trim() == "Bearer {token}" ne tient alors que par un espace en fin de chaîne (échoue « par chance »).
Impact
Faible : l'API est loopback (127.0.0.1:7654, is_loopback() en double-vérification) et désactivée par défaut. Mais une auth qui dépend d'un détail accidentel est à proscrire.
Recommandation
Si le token est vide/illisible → refuser toutes les requêtes (fail-closed explicite), au lieu de comparer une chaîne dégradée.
C

Robustesse & fiabilité

1 positif · 2 axes
C0PositifLa règle « Zéro unwrap » est quasi tenue—▶
Constat
Sur 286 occurrences brutes de unwrap/expect/panic, ~98 % sont dans des modules #[cfg(test)]. En production réelle : ≈5, toutes bénignes — SystemTime via unwrap_or_default() (pattern sûr), chain.last().unwrap() sur un vecteur prouvé non-vide (genesis), eligible.last().unwrap() après garde Some(..).
Pourquoi ça compte
Contredit la perception initiale d'un code « truffé d'unwrap ». L'idiome Result<T,E> + ? est réellement appliqué. Argument de qualité solide.
C1MoyenPas de fuzzing des parseurs réseaueffort M▶
Constat
proptest couvre des invariants (Shapley, overflow ledger), mais les surfaces d'entrée non fiables ne sont pas fuzzées : désérialisation GossipEnvelope (JSON depuis le réseau) et le parseur HTTP maison de la dev-API.
Impact
Un parseur écrit à la main sur entrée adverse est la source classique de paniques/DoS. C'est précisément là qu'un crash réseau peut survenir.
Recommandation
cargo-fuzz sur dispatch_incoming (bytes → envelope) et sur le parseur HTTP. Objectif : 0 panic sur entrée arbitraire.
C2FaibleDurcir les 5 unwrap résiduelseffort S▶
Constat
Ex. ledger.rs:480 self.chain.last().unwrap(), pos_consensus.rs:113/153. Invariants vrais aujourd'hui, mais implicites.
Recommandation
Remplacer par ? ou .expect("invariant: genesis present") documenté. Coût quasi nul, supprime tout doute lors d'une revue de sécurité.
D

Réseau P2P & consensus

1 positif · 2 axes
D0PositifProtocole riche et durci (NET-1 → NET-16)—▶
Constat
22 messages gossip, priority queue 4 voies, auto-reconnect, chain-sync parallèle, DAG incrémental, compression, métriques par pair, score qualité, vue topologie 2-hop, heuristique eclipse, rate-limit adaptatif, mempool TTL/cap.
Pourquoi ça compte
C'est un niveau de soin réseau rare pour un projet de cette taille. La logique est mûre.
D1ÉlevéConvergence prouvée en in-process, pas sur le transport réeleffort L▶
Constat
simulation.rs et integration_tests.rs (INT-1, « 3 nodes reach identical state ») prouvent la convergence logique : des ledgers en mémoire qui s'échangent des blocs par appel de fonction. Le « vérifié entre 2 machines » de la doc est un test manuel unique.
Impact
Non testés automatiquement : sérialisation réelle sur le fil (Iroh QUIC), traversée NAT, perte de paquets, churn de pairs, partition, pairs adverses. Or la mission V2 promet « convergence garantie ≤5 s » et « 0 perte » — affirmations non démontrées au niveau transport.
Recommandation
Harness multi-process en CI : spawn de N nœuds réels (vrais endpoints Iroh) sur la même machine, assertions de convergence, injection de fautes (kill/restart/latence). C'est l'investissement n°1 pour transformer « ça a marché une fois » en « c'est prouvé robuste ».
D2MoyenRésilience aux partitions non démontréeeffort M▶
Constat
La découverte/bootstrap et le comportement en cas de partition réseau (split-brain, re-merge de chaînes divergentes après reconnexion prolongée) ne sont pas couverts par des tests ni documentés comme garantie.
Recommandation
Documenter la stratégie de discovery (relays, bootstrap nodes), et ajouter un scénario de test « partition puis re-merge » s'appuyant sur le harness D1. Préciser la garantie réelle (convergence éventuelle, pas instantanée).

1 positif · 4 axes

E1ÉlevéClé de récupération non forcée sur le parcours principaleffort S▶
Constat
Le flux Welcome.onCreated entre directement dans l'app — commentaire assumé dans le code :
// +page.svelte:155
// Skip the forced recovery screen — go straight to the app.
ready = true;
Le parcours create classique, lui, force l'écran de sauvegarde + vérification du dernier bloc. Incohérence entre les deux chemins de création.
Impact
Un nouvel utilisateur peut entrer sans jamais sauvegarder sa clé maître — alors que l'UI elle-même prévient « Si vous la perdez, personne ne pourra récupérer votre compte ». Perte d'identité/fonds irréversible. Pour un produit crypto, c'est un défaut de sûreté, pas un détail UX.
Recommandation
Rendre l'affichage + la vérification de la clé obligatoires sur tous les chemins de création (y compris Welcome). Aucune entrée dans l'app sans confirmation de sauvegarde.
E2MoyenFrançais figé en dur, zéro i18neffort M▶
Constat
Tout le texte d'interface est codé en dur en français ; aucune couche i18n, aucun sélecteur de langue.
Impact
Incompatible avec une ambition « google web3 » mondiale. Barrière d'adoption immédiate hors francophonie.
Recommandation
Extraire les chaînes vers un dictionnaire (clé → texte), i18n minimal fr/en avec détection système. Pas besoin de framework lourd ; une petite store Svelte suffit.
E3MoyenPageBuilder monolithique (3 113 l.)effort M▶
Constat
Le builder no-code (20 types de blocs, 5 thèmes, 5 templates, undo/redo, preview responsive) tient dans un seul fichier de 3 113 lignes.
Impact
Le composant le plus précieux du produit (« créer un site en 1 clic ») est aussi le plus risqué à faire évoluer. Chaque nouvelle feature accroît la dette.
Recommandation
Extraire : registre de blocs, rendu de bloc, toolbar, gestion thèmes/templates, store d'historique. Tester les blocs isolément.
E4MoyenSurface backend >> profondeur produiteffort M▶
Constat
70 commandes backend exposent forums, marketplace compute, modération par jury VRF, trust graph, domaines .torus… La maturité UX de ces surfaces est très inégale par rapport au cœur (wallet, builder, browser).
Impact
Risque de « 10 demi-fonctionnalités » au lieu de 2-3 parcours excellents. Un produit perçu comme pro fait peu de choses, parfaitement.
Recommandation
Choisir 2-3 parcours « héros » (ex. publier un site .torus, miner/recevoir des QUANTA, chercher/naviguer le web P2P), les polir à fond, et marquer le reste comme « expérimental » dans l'UI plutôt que de l'exposer au même niveau.

Prod-readiness

1 positif · 3 axes
G0PositifUpdater OTA réellement configuré—▶
Constat
tauri.conf.json : createUpdaterArtifacts: true, plugin updater avec clé publique minisign réelle + endpoints. CI présente (cargo check/test/clippy -D warnings + npm build).
Pourquoi ça compte

G1ÉlevéPas de pipeline de build/release/signatureeffort M▶
Constat
Workflows présents : ci.yml, claude-review.yml. Aucun workflow de release. L'updater attend des artefacts GitHub Release signés, mais rien ne les construit/signe automatiquement → releases faites à la main sur le Mac du dev.

Recommandation
